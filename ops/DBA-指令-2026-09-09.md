## 背景（30 秒）

今天上午 v1.5.21 上线后生产瘫了 4 分钟，全部落库端点 500。原因是应用在**每个请求
路径上**执行 DDL，而应用账号没有 ALTER 权限：

```
(1142, "ALTER command denied to user 'goku_router_owner'@'10.3.84.121'
        for table 'request_logs'")
```

已由 DBA 补上 `request_logs.created_at` 后自愈。v1.5.23 从代码侧修掉了这个模式：
迁移只在启动时跑一次，且**模型与库不一致时拒绝启动**（起不来比每个请求 500 好诊断）。

## 第 2 步：清空遥测表 + 加 provider_id

> 决策：chenbin 2026-09-09。**不可逆，不做备份**（明确选择）。
> 依据与取舍详见 `ops/DBA-provider-id-migration-2026-09-09.md`。

```sql
-- ① 清空两张遥测表
TRUNCATE TABLE request_logs;
TRUNCATE TABLE provider_quality_scores;

-- ② 加列（可空）
ALTER TABLE request_logs            ADD COLUMN provider_id INT NULL;
ALTER TABLE provider_quality_scores ADD COLUMN provider_id INT NULL;

-- ③ 索引
CREATE INDEX ix_request_logs_provider_id            ON request_logs (provider_id);
CREATE INDEX ix_provider_quality_scores_provider_id ON provider_quality_scores (provider_id);
```

**不加外键约束。** `request_logs` 是高写入表，而 `providers.avg_latency_ms` 每次
成功请求都在更新。FK 会让子表 INSERT 对父表持共享锁、父表 UPDATE 要排他锁 ——
正是 core 侧 2026-09 那次 MCP 遥测死锁的模式。

### 会失去什么（已确认接受）

- 分析页、账单**用量页**归零（`/admin/billing/usage` 读的是 `request_logs`，
  不是 `billing_records`），累计 $273.8 的用量明细在界面上消失；
- `billing_records` 表**不动**，原始账目仍在库里，只是当前没有接口读它；
  月度汇总 `billing_summaries` 是独立表，不受影响；
- 2026-09-08 那批 Qwen3.8 的 503 故障记录一并清除。

## 第 4 步：部署后确认（SRE）

```bash
curl -s https://goku-router.starboss.biz/admin/system/info
```

预期 `{"version":"v1.5.23", ...}`。

**如果 Pod 起不来**，看日志第一行 —— v1.5.23 会直接打出缺哪一列、要执行什么：

```
SCHEMA_MISMATCH <表>.<列> —— 模型声明了该列但数据库没有。
请 DBA 执行: ALTER TABLE <表> ADD COLUMN <列> <类型> NULL;
```

把这行发回来即可。这比上午那种「服务活着但每个请求 500」好诊断得多 ——
那次要翻完整段 traceback 才知道是加列引起的。

## 长期建议（不急，供讨论）

`ensure_schema` 里有一张手写的 ALTER 清单，本仓库**没有 Alembic**
（README 此前写着 `alembic upgrade head`，是错的，今天已更正）。当前约定是：
**凡新增列，先找 DBA 执行 DDL，再发代码。**

两条路可选，我倾向前者：

1. **维持现状**：应用账号不给 ALTER 权限，加列走 DBA。v1.5.23 的启动自检让遗漏
   立刻可见，代价可控。
2. 给应用账号 ALTER 权限让它自举 —— 但「应用能随时改生产 schema」本身是更大的
   风险面，不建议。
